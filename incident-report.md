# Incident Report: Suspicious Scheduled Task Persistence

## Incident Summary

Microsoft Sentinel generated a High-severity incident after detecting the creation of a suspicious Windows Scheduled Task.

The incident was generated by the custom analytics rule:

`Suspicious Scheduled Task Persistence`

The activity was created intentionally in a controlled lab environment to simulate persistence through Windows Scheduled Tasks.

The detection focused on newly created Scheduled Tasks that used suspicious executables, scripting interpreters, command shells, LOLBins, or task paths outside the standard Microsoft Scheduled Task namespace.

---

## Affected Assets

### Host

`win-blue-team-lab`

### Account

`azureuser`

The incident was enriched using Host and Account entity mapping in Microsoft Sentinel.

---

## Detection Source

The detection was based on Windows Security Event ID:

`4698 — A scheduled task was created`

Windows audit policy for Other Object Access Events was enabled to ensure Scheduled Task creation was recorded.

The event was collected through:

- Windows Security auditing;
- Azure Monitor Agent;
- Data Collection Rule;
- Log Analytics;
- Microsoft Sentinel.

---

## Controlled Persistence Simulation

A Scheduled Task was created in the lab using:

```powershell
schtasks /create /tn "BlueTeam-Lab-Persistence" /tr "cmd.exe /c echo Scheduled task executed > C:\Temp\scheduled-task-test.txt" /sc ONSTART /ru SYSTEM /f
```

The task was configured to:

- run at system startup;
- execute under the `SYSTEM` account;
- launch `cmd.exe`;
- execute a harmless test action.

The task was created only for controlled security testing.

---

## Event Investigation

Event ID `4698` contained the Scheduled Task configuration inside the `EventData` field.

The investigation extracted:

- SubjectUserName;
- SubjectDomainName;
- TaskName;
- TaskContent;
- Command;
- Arguments;
- RunAsUser.

The simulated task showed:

- task name outside the Microsoft Scheduled Task namespace;
- command execution through `cmd.exe`;
- execution under the local SYSTEM account.

---

## Detection Classification

The detection classified newly created Scheduled Tasks using several behavioral indicators.

Potentially suspicious activity included:

- PowerShell execution;
- command shell execution;
- script interpreter execution;
- LOLBin execution;
- task creation outside the `\Microsoft\` namespace.

The controlled lab task was classified as:

`Command shell execution`

---

## Detection Logic

The final analytics rule used the following KQL:

```kql
SecurityEvent
| where EventID == 4698
| extend SubjectUserName = extract(@'<Data Name="SubjectUserName">([^<]*)</Data>', 1, EventData)
| extend TaskName = extract(@'<Data Name="TaskName">([^<]*)</Data>', 1, EventData)
| extend TaskContentRaw = extract(@'<Data Name="TaskContent">([\s\S]*?)</Data>', 1, EventData)
| extend TaskContent = replace_string(
    replace_string(
        replace_string(
            replace_string(TaskContentRaw, "&lt;", "<"),
            "&gt;", ">"
        ),
        "&quot;", "\""
    ),
    "&amp;", "&"
)
| extend Command = extract(@"<Command>([^<]+)</Command>", 1, TaskContent)
| extend Arguments = extract(@"<Arguments>([^<]+)</Arguments>", 1, TaskContent)
| extend RunAsUser = extract(@"<UserId>([^<]+)</UserId>", 1, TaskContent)
| extend SuspiciousReason = case(
    Command has_any ("powershell.exe", "pwsh.exe"), "PowerShell execution",
    Command has "cmd.exe", "Command shell execution",
    Command has_any ("wscript.exe", "cscript.exe"), "Script interpreter execution",
    Command has_any ("mshta.exe", "rundll32.exe", "regsvr32.exe"), "LOLBin execution",
    TaskName !startswith @"\Microsoft\", "Task outside Microsoft namespace",
    "Other"
)
| where SuspiciousReason != "Other"
| project
    TimeGenerated,
    Computer,
    SubjectUserName,
    TaskName,
    Command,
    Arguments,
    RunAsUser,
    SuspiciousReason
```

## Incident Findings

The investigation confirmed that:

- a new Scheduled Task was created on `win-blue-team-lab`;
- Event ID `4698` was generated;
- the event was successfully ingested into Microsoft Sentinel;
- the task configuration was extracted from XML event data;
- the task executed `cmd.exe`;
- the task ran under the SYSTEM account;
- the task was created outside the standard Microsoft namespace;
- the analytics rule classified the activity as suspicious;
- Sentinel generated a High-severity incident;
- Host and Account entities were mapped correctly;
- the affected account was `azureuser`.

---

## Analyst Assessment

The behavior detected in this incident would require investigation in a production environment.

Scheduled Tasks are commonly used for legitimate administrative purposes, but they are also frequently abused for persistence.

The presence of a Scheduled Task alone is therefore not enough to confirm malicious activity.

Relevant investigation context should include:

- task name;
- task path;
- executable;
- command-line arguments;
- task trigger;
- account that created the task;
- account used to execute the task;
- related process creation events;
- authentication activity;
- endpoint history;
- network activity;
- EDR telemetry;
- whether the task is part of approved software or administration.

## Manual Remediation

After the incident was investigated, the controlled persistence mechanism was manually removed from the endpoint.

The Scheduled Task was deleted using:

```powershell
schtasks /delete /tn "BlueTeam-Lab-Persistence-Final" /f
```

A follow-up query confirmed that the task no longer existed.

The associated test artifact was also removed:

```powershell
Remove-Item "C:\Temp\scheduled-task-final.txt" -ErrorAction SilentlyContinue
```

This remediation was performed only after analyst validation.

The same controlled lab VM was used for both attack simulation and defender-response activities.

## Automated Analyst Triage

A Microsoft Sentinel automation rule was created:

`Scheduled-Task-Persistence-Triage`

The automation rule was configured to run:

`When incident is created`

It applied only to incidents generated by:

`Suspicious Scheduled Task Persistence`

The automated action created the analyst task:

`Validate and remove suspicious scheduled task`

The task instructed the analyst to:

- review the scheduled task name;
- review the command and arguments;
- validate the affected host and account;
- determine whether the task was authorized;
- remove the task if malicious or unauthorized;
- confirm that the task no longer existed;
- review related endpoint and authentication activity;
- determine whether additional containment was required.

The automation rule intentionally did not perform destructive remediation automatically.

---

## Recommended Response

For a similar production incident, the analyst should:

1. Validate the Scheduled Task name and path.
2. Review the command and arguments.
3. Identify the account that created the task.
4. Confirm the account used to execute the task.
5. Review the trigger and execution schedule.
6. Search for related process creation activity.
7. Review authentication activity around the same time.
8. Determine whether the task is part of approved software or administration.
9. Search the endpoint for related persistence mechanisms.
10. Determine whether containment is required.

If malicious activity is confirmed:

- delete the unauthorized Scheduled Task;
- terminate related malicious processes where appropriate;
- isolate the affected endpoint if compromise is active;
- disable or reset compromised accounts;
- search for similar Scheduled Tasks across other systems;
- review lateral movement;
- preserve logs and forensic evidence;
- continue incident response and threat hunting.

---

## Detection Limitations

The detection is intentionally broad for lab purposes.

Potential false positives include:

- legitimate administrative Scheduled Tasks;
- software deployment tools;
- backup applications;
- monitoring agents;
- enterprise management platforms;
- approved scripts using command shells or PowerShell.

Production improvements could include:

- known-good task allowlists;
- trusted administrative account baselines;
- approved task path baselines;
- signer and executable reputation;
- command-line reputation;
- parent-process analysis;
- process creation correlation;
- task creation frequency;
- EDR telemetry;
- user behavior analytics.

Automatic deletion should not occur without validation because legitimate Scheduled Tasks may match the same indicators.
